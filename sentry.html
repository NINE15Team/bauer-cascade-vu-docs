Sentry

Error tracking for the Bauer customizer. Instrumented so an S3 failure, a CORS'd thumbnail or a dead cart POST arrives with region, product, theme role and engine build attached. Cascade has no equivalent.

Do not optimise this file

The Sentry tags are classic blocking scripts, above the inline injector that pulls VU's main.js. Adding defer or async means the engine's fetches are never instrumented — tracking silently reports nothing while appearing healthy.

Why it exists

The engine is an opaque third-party bundle on S3. Theme JS cannot observe its GLB, texture or recipe failures unless something is initialised before it runs. vu_sentry.js is that something — it wraps fetch and installs capture-phase listeners early enough to see everything the engine does afterwards.

It also has to survive ad blockers. If the Sentry CDN is blocked, the file installs a no-op window.VuSentry so vu_main.js and the snippet's handleError do not throw.

Load order

Top of vu_customizer_snippet.liquid. This sequence is load-bearing:

  1. window.vuSentryConfig — Liquid-filled: environment, variant, variantId, locale, shop, main_source_url
  2. browser.sentry-cdn.com/10.67.0/bundle.min.js (SRI)
  3. browser.sentry-cdn.com/10.67.0/httpclient.min.js (SRI)
  4. vu_sentry.js — theme asset, blocking
  5. vu_main.js — deferred
  6. Inline loadScript(main_source) — injects the S3 engine during parse
SRI is pinned

Bumping the CDN version without updating both integrity attributes fails closed — correct behaviour, but it disables tracking silently. Test version bumps on a draft theme.

Shopify auto-minifies theme JS and serves a public source map, so stack traces resolve without extra upload steps.

Environments

Two different things named “environment”

Sentry environment = shopper exposure, derived from shop domain + theme role. vu_engine = which engine build loaded, from settings.vu_customizer_environment. They are independent. Alert on the first; never gate on the second.

BucketConditionAlerting
stagingShop domain matches *-dev.myshopify.comNever. Noise.
production-draftLive shop, theme role ≠ mainNo. Watch during launches.
productionLive shop + published main theme, or theme role unreadableThe only bucket prod alerts fire on.

Publishing a draft theme flips production-draft → production. If theme role cannot be read on a live shop we fail toward production, so real incidents are never hidden.

Region fallback when customizer_values.country is empty: hostname/shop string is scanned for bauer-ca/ca., se, fi, dk, else us.

Capture paths

  1. httpClientIntegrationHTTP 400–599 on VU S3 hosts, vucustom.com, the recipe image API, and /cart/add.

  2. Capture-phase errorOn script/link/img whose URL matches the VU regex. These never reach window.onerror.

  3. customizer.add-to-cart-failVU's own event. Detail JSON truncated to 2k chars.

  4. Wrapped fetchVU or cart URLs rejecting with a bare TypeError (CORS / DNS / offline). httpClient never sees these. The rejection is rethrown after capture.

  5. Snippet handleErrorS3 main.js onerror → VU main.js failed to load.

  6. 80s scene timeoutvu_main.js openPopUpModal (L1631/1635) → VU scene render timeout (80s) plus the failed-loading UI.

Deliberately absent

No manual unhandledrejection listener. The SDK's global handlers already capture rejections; adding ours double-reports. If you see duplicates, check whether one was re-added.

VU-related URL matcher: vu-customizer.s3.amazonaws.com | vu-admin.s3.amazonaws.com | s3.amazonaws.com/vu-os | vucustom.com | vu_main.js | vu_sentry.js | vu_customizer_restore_selections.js.

Filters

ignoreErrors: ResizeObserver loop, non-error promise rejection, Script error., globalThis is not defined, in-app browser bridges (instantSearchSDKJSBridgeClearHighlight, window.webkit.messageHandlers).

denyUrls: GTM, GA, DoubleClick, Klaviyo, Facebook, LinkedIn, Bing, all browser extensions.

Thumbnail 4xx stay under asset_load with vu_asset_kind=thumbnail, so the existing 403/CORS rule still matches them.

Cross-environment grouping

Issues group across environments, so an error first seen in production-draft is not “new” when it later occurs in production — the new-issue rule stays silent. Delete test issues before go-live. Use plain Delete, not delete-and-discard.

Known vendor-side behaviour

Worth checking with VU before digging into the theme

During rollout the engine was seen requesting vu-os/staging/templates/null_en-us.json and receiving a 403 on supreme-fuse — a VU-side permissions issue, not a theme one. Separately, customizer.vucustom.com had a genuine CORS outage in July 2026 that VU fixed.

A sudden burst of network failures with no corresponding theme change is worth raising with VU first.

Verification

  • Preview a draft theme on a live shop → environment should be production-draft.
  • Load a *-dev shop → staging.
  • Block the Sentry CDN in DevTools → the customizer must still open; VuSentry.enabled === false.
  • Set an invalid environment to force an S3 404 → VU main.js failed to load plus the failed-loading UI.
  • Confirm tags (region, product, theme role) are populated on a real event.
